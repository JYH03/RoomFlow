## 빠른 시연 (Swagger, 약 5분)

1. README대로 서버를 시작하고 /swagger-ui/index.html에 접속합니다.
2. 새로운 이메일로 사용자 A·B를 회원가입하고 각각 로그인합니다.
3. Authorize에 A의 토큰을 입력하고 비어 있는 방의 **내일 14~15시**를 예약합니다. 응답 예약 id를 기록합니다.
4. Authorize를 B 토큰으로 바꾸고 같은 방·시간에 대기를 등록합니다. position=1을 확인합니다.
5. A 토큰으로 예약을 취소합니다.
6. B 토큰으로 GET /api/reservation-offers를 조회합니다. PENDING 제안의 id를 확인합니다.
7. 10분 안에 POST /api/reservation-offers/{id}/accept를 실행합니다.
8. GET /api/reservations에서 B의 CONFIRMED 예약을 확인합니다.
9. 같은 제안을 다시 수락하면 409인지 확인합니다.

방 id는 방 목록 응답에서 확인하세요. roomNumber와 DB id가 항상 같다고 가정하지 않습니다. 기존 사용 중인 슬롯과 실제 계정은 건드리지 말고 시연용 계정을 사용하세요.

내일 예약은 아직 체크인할 수 없어 400이 정상입니다. 자동 테스트에서는 시간을 조정한 **격리 DB fixture**로 체크인·노쇼·완료·만료를 검증하므로 직접 개발 DB 시각을 바꿀 필요가 없습니다.

거절 시연은 C 계정을 추가해 B 뒤에 대기시킨 다음, B가 제안을 거절하여 C에게 새 제안이 생성되는지 확인합니다. 만료는 PENDING 기한 이후 스케줄러 주기까지 기다리면 됩니다.

시연용 회원·예약·대기 기록은 이력으로 남습니다. 자동 삭제 스크립트는 제공하지 않습니다.

## 기존 환경에서 달라진 점

- Swagger가 실제로 추가됐습니다.
- 내 예약/제안 목록, 제안 거절 API가 추가됐습니다.
- 대기 응답에 현재 순위 position이 추가됐습니다. queueOrder는 기존 발급 순번입니다.
- 중복·상태 충돌은 409로 구분합니다.
- 신규 예약·대기는 미래 정시부터 정확히 1시간으로 검증합니다.
- 제안은 시작 시각을 넘어도 생성부터 최대 10분을 보장하되 이용 종료에 잘립니다.
- 시작 후 일반 예약은 불가, 기존 대기자의 제안 수락은 가능합니다.
- 종료된 CHECKED_IN은 COMPLETED, 남은 활성 대기는 EXPIRED로 정리합니다.
- 같은 방에 대한 변경 작업은 잠금으로 보호됩니다.
- 기존 DB 설정 파일은 외부 파일로 읽으며 JAR에는 넣지 않습니다.

기존 다섯 테이블 구조를 사용하므로 기존 DB를 지우거나 신규 설치 SQL을 다시 실행할 필요는 없습니다. 기존 스키마가 earlier Day 모델과 다르면 validate 오류를 먼저 확인하고 데이터 보존을 전제로 수정하세요.
